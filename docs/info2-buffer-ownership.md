## Open questions

- What physical depth storage corresponds to the configured eDRAM translation, and which independently reserved or owned VRAM ranges can be established?

  Deferred from the unresolved extent portion of the first hand-off's buffer/view question. Keep the linear depth envelope and apparent `0x8000` gap qualified until the mapping is established. Begin with local SDK/reference material and game/API setup; report a hardware/emulator-semantics limitation if physical backing cannot be proven. Do not invent allocator blocks for fixed addresses or assume a texture declaration reserves its nominal span.

  Runtime evidence (zone render modes 0, 2, 3, and 4, see "Observed zone frames"): the configured translation is `0x1000`. In every observed frame, the game keeps its 64x64 RGB565 character shadow texture at `0x20780`, stride 1024, alive from its production to the shadow quad draw, across the full-scene clear and world pass that write depth 0/512. Under a linear 16-bit depth layout, those depth writes would cover the first 32 texels of every block row, rows 129..255 (odd) at x 448..479. Either the translated physical depth placement avoids that range, or the game tolerates the damage; the capture cannot tell which. The torch composite uses a second depth buffer at `0x1C0000`, stride 512. Reference follow-up below establishes the CPU-mirror permutations and PPSSPP's non-emulation of the translation. The GE-depth-to-mirror relation remains unproven: the `0x04600000` candidate avoids the shadow block and reaches the upper half of the apparent gap, but these are conditional derived results, not established physical ownership. User observation, PPSSPP software renderer (which stores GE depth linearly in emulated VRAM and ignores the translation): a purple, striped area replaces exactly the texture-left half (u 0..31) of the projected character shadow, and the other half shows the intact silhouette. That is precisely the damage predicted for the ordinary linear layout. Since the retail game is not known to show this artifact on hardware (not verified here), the observation argues against the ordinary and `0x04200000` layouts for GE depth and is consistent with the `0x04600000` candidate; it does not prove it. See `docs/ppsspp/emulation-issues-overview.md`. The flare-query pixels show the same pattern (derived): `0x04000780 + 4*lightId` is linear depth pixel (448, 1) onward, but under the `0x04600000` candidate it maps to depth row padding (row 32, x 496 onward for light 0), like the shadow block.

### Baseline allocation, teardown, and clear-policy ownership

- Which storage persists for the renderer lifetime, and which contents are cleared, overwritten, preserved, or invalidated?

Static answer for the baseline path: fixed VRAM views, RAM presentation recordings, and RAM scene-command allocations have different ownership. Ordinary presentation reuses them; the explicit device-stop path releases the scene-command ring but does not reclaim the display pool in the inspected code.

| Storage/view | Creation and ordinary lifetime | Inspected stop behavior |
| --- | --- | --- |
| Scene/depth/RGB565 images | Fixed game-visible VRAM addresses established by setup and pool recording; not separate allocator-returned image blocks | No image free, memset, or clear primitive in the device-stop chain |
| Display-entry metadata | `0x0017DC2C` allocates 0x48 RAM bytes through the RenderWare memory interface, zeroes metadata, initializes two stamps to -1 | No free of the array pointer `0x00587B64` in the stop chain; raw references found only initialization/selection/thread accesses |
| Two presentation list/vertex blocks | `0x0017FFF4` allocates 0x1E60 RAM bytes per entry for the 480-pixel case; raw pointers at entry+8, aligned CALL pointers at entry+4 | No traversal/free of these entry fields in the stop chain |
| Scene-command ring | `0x0017D5AC`: initialized count 2; 0x20-byte RAM metadata plus two 0x100040-byte raw allocations, each aligned to 64 bytes; sizes derive from defaults at `0x004F4A08/0x004F4A0C` | `0x0017D9CC` frees each raw pointer, zeroes raw/aligned fields, frees metadata, nulls `0x005894B4`, and clears active flag `0x004F4A04` |
| Ordinary VRAM allocator metadata | `0x00180CDC` allocates/zeroes a separate count*12 RAM record array at `0x00586B08`; not the display array | `0x00180E4C` passes that array pointer to the hook at `RwGlobals+0x10C`; it does not clear this global afterwards |

The memory-interface pointer is stored at `0x00589484`; ring/pool allocations use its first hook and ring reclamation its +4 hook. Scene-ring allocation failure frees previously created raw blocks and metadata before returning 0. The device-start caller does not inspect that return value, so successful initialization/allocation is a precondition of the normal path, not something established for every error branch. [Static: `0x0017AF5C` case 4, `0x0017D5AC` C/assembly, `0x0017D9CC` C/assembly, `0x0017DC2C`, `0x0017FFF4`, defaults at `0x004F4A04..0x004F4A13`.]

The ordinary VRAM allocator's game-side boundary is also recoverable: mode 0 selects `start=((B+0x173FFF)&0xFFFF0000)+0x80000` and capacity `B+edramSize-start`. For the expected B=`0x04000000` and 2 MiB, this starts at offset `0x1F0000` with 0x10000 bytes available. This excludes the fixed baseline views from that allocator's returned range; it does not prove the physical depth transform or identify every owner below the boundary. Modes 1..3 use another boundary. [Static: `0x00180CDC`, API-base/size getters `0x0017E790/0x0017E7A0`; returned base/size remain runtime-dependent.]

```text
device-system case 3 -> 0017AE0C
  00180E4C: release ordinary VRAM allocator's RAM metadata through its hook
  0017D9CC: release scene-command ring and clear its active flag
  0017A0E4: sceGeEdramSetAddrTranslation(0)
  0017FFC0: delete RwPspDLSignal semaphore and unset GE callback
```

The stop bodies have no display-thread termination or display-entry/list free. Raw-reference scans of `0x00587B58`, `0x00587B64`, and `0x004F48A8` found no pool reclamation or one-time-flag reset. This supports "not reclaimed by this stop path," not a whole-program leak diagnosis. A later device start skips the guarded `0x0017FE9C` call because `0x004F48A8` was cleared on initial start; it still performs device-state setup and recreates the freed scene ring. This does not establish that repeated stop/start is fully supported: callback/semaphore re-registration and display-thread lifetime are not repaired by the inspected restart path. [Static: `0x0017AF5C`, `0x0017AE0C`, `0x00180E4C` assembly, `0x0017D9CC`, `0x0017A0E4`, `0x0017FFC0`, `0x0017ADA8`; raw scans are not exhaustive for computed/indirect accesses.]

### One target/depth restoration boundary

- How are scene target/depth bindings restored across camera and offscreen-pass boundaries, and when do cached context fields diverge from effective GE state?

Static answer for one selected boundary: the FX worker's mode-2 renderer `0x000F0460` explicitly transitions scratch target code 10 back to scene code 0. On iteration 0 it first copies scene into scratch; subsequent iterations skip that producer and still restore/bind scene before consuming scratch. The effect's filtering/composition algorithm is outside this trace.

```text
000F0DAC: worker mode == 2 -> 000F0460
  if iteration (+08) == 0:
    000F0588: target selector(10) -> scratch color; shared depth 0/512
    000F05E4: PRIM reads fixed scene and writes scratch
  000F05EC: target selector(0) -> fixed scene color; shared depth 0/512
  000F0618 / 000F0620: bind scratch texture and flush
  000F0638: PRIM consumes scratch in scene
  return -> worker calls ordinary presentation helper 0017D7CC
```

| Bound field | Code 10 | Code 0 |
| --- | --- | --- |
| Color format/stride | RGBA8888 / 512 | RGBA8888 / 512 |
| Framebuffer pointer argument | `0x170000` offset (expected VRAM view `0x04170000`) | `B + persistentSceneOffset` (mode 0: `0x0404C000`) |
| Emitted depth pointer/stride | 0 / 512 | 0 / 512 |
| Offset/viewport | offset `0x710,0x778`; viewport center `0x800,0x800`, dimensions 480x272 | Same baseline values |
| Requested scissor/region | 480x272 at origin | Same baseline rectangle; emission depends on the scissor-enable context flag |

This boundary changes color storage and explicitly reasserts depth; it does not switch to a private depth image. `0x00187390` emits target/depth commands through `0x0017F7A8` and `0x0017F96C` in both branches. Framebuffer binds update cached format at `0x00587A88` but do not change persistent scene offset `0x00587A60`; depth binds store 0/512 to `0x00587A68/0x00587A6C`. They therefore repair the initialization-time cached-depth divergence described in step 1. Binding/restoration does not clear either image and does not save/restore all draw state. Emitted state becomes effective on GE execution, not at the CPU cache-field store. [Static: `0x000F0DAC`, `0x000F0460`, slices at `0x000F0588/0x000F05EC`, `0x001873BC..0x00187480`, emitter assembly `0x0017F7A8/0x0017F96C/0x0017DE9C`, `0x0017DF8C/0x0017DE08`.]

The scratch producer/consumer order is established for this code path, not for every user of `0x170000`. Runtime activation, physical overlap under translation, and inherited pixel masks/tests remain checks. Its trigger and the other bounded target users are identified below; effect algorithms remain outside scope.

### Ordinary allocator: callers, gate, sizes, and code-10 overlap

Static: `0x00180CDC` sets up `[0x041F0000,0x04200000)` in device mode 0, with 32 twelve-byte RAM records (0x180 bytes; default count at `0x004F4E24`). The allocator context is at relocation-corrected `0x00586AF0`: +0 base, +4 capacity, +8 next pointer, +0xC record count, +0x14 newest record, +0x18 RAM records pointer, +0x1C enable gate. At `0x00180E08` successful initialization writes **zero** to that gate (`0x00586B0C`). The separate `0x004F4E20=1` store marks initialization, not VRAM allocation permission.

`FUN_00180E88(size)` returns the RenderWare RAM hook's result while the gate is zero; only a nonzero gate reaches `FUN_00180BC0(size)` at `0x00180ED0`, then falls back to RAM if the pool fails. Assembly is essential because its decompiled return type is void. The pool appends a record containing returned start/older/newer, and advances next to `(start+size+0x3F)&~0x3F`; the available-size check precedes alignment. `FUN_00180F10(ptr)` routes VRAM frees to `0x00180B34` and other frees to the RAM hook. Pool free unlinks the record and rewinds next only for the newest block; it does not clear image bytes or provide GE-completion synchronization.

### Physical depth reference result and conditional arithmetic

Static reference: the requested `tools-thirdparty-readonly/pspsdk` path is absent. The available SDK fragments are under `tools-thirdparty-readonly/psp-sdk`, including `gimconv/src/GimConv/Sample/ExportGIP/include/geman.h:283..285` and `libgu.h:510..511`. Hardware-recorded reference, not a new observation here: `D:/Code/Repos/ppsspp-experiments/ppsspp-src/pspautotests/tests/gpu/ge/edramswizzle.cpp`, `validatePattern1000`, and its `.expected` establish the following byte permutations for translation `0x1000`. Let `p` be an offset in the ordinary `0x04000000` CPU view and `j` the mirror offset holding that same byte:

```text
0x04200000: j = p ^ 0x8040
0x04400000: j = p
0x04600000: j = ((p ^ 0x8000) & ~0x0FE0)
                 | ((p & 0x0F80) >> 1)
                 | ((~p & 0x0040) >> 1)
                 | ((p & 0x0020) << 6)
```

The test writes CPU VRAM, invalidates caches, and compares all mirror bytes. It does **not** draw through ZBP, so it does not prove that GE depth at logical offset j writes ordinary-view offset `inverse(j)`.

PPSSPP reference, agreeing with the supplied session finding: `GPU/GPUCommon.cpp:720..727` only swaps/stores and returns `edramTranslation_`; `GPU/Debugger/Record.cpp:614` records it. The additional serialization at `GPUCommon.cpp:1522` is state bookkeeping, not a transform. `TextureCacheCommon.cpp:1171` associates depth with mirrors `0x04200000/0x04600000`; `:1392..1393` selects an X permutation for mirror 2 with 8888 colour; `:1969..1977` approximates mirrored texture reads by toggling texture swizzle and explicitly notes mirrors 2 and 6 differ. `DepalettizeShaderCommon.cpp:52..65` treats mirror 6 as the unpermuted host-depth-texture case. `FramebufferManagerCommon.cpp:744..749` and `Draw2D.cpp:141..159` apply a compatibility-specific four-row reversal for colour-to-depth copies.
